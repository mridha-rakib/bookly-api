# Platform bank account — separately authorized read-only verification

Prepared 8 November 2026. **These steps were not executed.** They require a separately authorized operator with the appropriate Bookly Super Admin and Stripe platform access. They do not authorize withdrawals, bank changes, schedule changes, broader API-key grants or production activation.

1. Identify the intended deployed API environment and legal-entity Stripe platform account. In Stripe Dashboard, select that account explicitly. Independently confirm whether the intended environment is TEST or LIVE. Do not infer mode, API permissions or verification from the Owner's bank screenshot.
2. Open `https://dashboard.stripe.com/settings/payouts` in that account. Read the bank/settlement settings: bank name, masked last four, country, currency, default-for-currency designation, bank status and any payout/verification restrictions. Record masked observations only. Do not reveal, copy or retain a full account identifier or identity documentation.
3. Using the existing authenticated Bookly Super Admin session/API client against that same deployment, issue exactly **GET `/super-admin/finance/withdrawals/bank-account`**. Retain only its masked JSON result and a UTC observation timestamp. Never paste a bearer token, cookie, provider key or raw provider error into a report or shell history.
4. Check `managedBy`, credential `mode`, `state`, `inventoryComplete`, `unavailableReason`, `payoutsEnabled` and each returned destination's bank name/last4/currency/country/status/default flag. Match the independently observed Dashboard destination. Order is not authority: verify the provider-designated default for every currency. An incomplete list or duplicate defaults cannot confirm default selection.
5. If the summary is unavailable, partial or empty while Dashboard shows a bank, keep the result unresolved. Review only the authorized key's account binding/permissions and the adapter/API compatibility with the provider administrator. The installed adapter uses `accounts.retrieveCurrent()` (`GET /v1/account`) and, when needed, `accounts.listExternalAccounts(returnedAccountId, {object: 'bank_account', limit: 100, starting_after?})`, bounded to three pages. It never supplies a connected-account override. Access to the latter resource is account/key-model dependent. Do not substitute a Business destination, Customer card or screenshot value, and do not broaden permissions as part of this checklist.
6. To confirm error isolation separately, issue read-only **GET `/super-admin/finance/withdrawals/overview`**. Its balance/history/liability result may fail independently of the bank summary. If it succeeds, available and pending balances remain provider facts, recent pending/in-transit totals remain a bounded sample, and Business-attributed unpaid funds remain an informational accounting input. None is a proven eligible platform withdrawal amount.
7. Confirm the overview reports effective `liveExecutionEnabled: false` and the relevant restrictions. Confirm the UI distinguishes Platform Bank Account, Stripe balances, eligibility/restrictions, reserve status and withdrawal history. Do not submit any payout form or use a mutating endpoint to test denial in production.
8. For authorization verification, use only existing separately authorized test-role sessions to request the same bank GET: anonymous must return 401, Customer/Business Owner/Supervisor/Staff must return 403, and an active authenticated Super Admin may read the masked summary. Do not create accounts or alter roles for this procedure. If such sessions are unavailable, retain that item as unverified; mocked role coverage already exists.
9. Record pass/fail/unverified results, environment, UTC observation times, masked bank facts, mode/account-match evidence and unresolved API permissions/verification issues. Have the operator/account owner review discrepancies. A successful read confirms only the observed read contract at that time.

**Never run** POST `/super-admin/finance/withdrawals`, POST withdrawal refresh/recovery routes, Stripe Payout creation, bank mutation, credential rotation, a worker, migration or index synchronization under this read-only procedure. Some recovery POSTs can resend TEST operations and are deliberately excluded.

Provider facts still requiring this verification include the actual deployed key's account/mode, API visibility of the Dashboard bank, complete default/currency inventory, payout-enabled status and required provider verification. Eligible funds and LIVE execution additionally require an approved reserve policy, race-safe implementation and separate release authorization. See `CENTRAL-WITHDRAWAL-RESERVE-DECISION.md`.

Reference: [Stripe external bank-account list](https://docs.stripe.com/api/external_account_bank_accounts/list) describes paginated account external-bank reads; [Stripe account retrieval](https://docs.stripe.com/api/accounts/retrieve) describes the Account response. These documents do not prove this platform key can access those resources.
